## Source conflicts surfaced

Resolved: command union = add, update (name/kind/technology/metadata), remove, connect (with relationship/metadata), disconnect, insert, rename, reset; highlight/explain are transient/advisory; group/undo/layout per D06/P2.
2. I2 "remove incident edges" vs prototype bridging: resolved by P1.
3. Prototype Gemini tool enum omits `external`: server schema includes it.

## I1 contract choices (2026-10-05, default)
- Schemas live in `shared/src` (Zod 4). NodeKind uses UPPERCASE per the LLD; `NODE_KIND_FROM_LEGACY` maps prototype lowercase types.
- Commands: ADD_NODE, REMOVE_NODE, RENAME_NODE, UPDATE_NODE (kind/technology/metadata; `technology:null` clears; metadata replaces), CONNECT, DISCONNECT (edgeId XOR source+target), INSERT_BETWEEN (optional edgeId), RESET. All schemas are strict (unknown fields rejected). New-node commands carry no id; the server assigns UUIDs (D04).
- Version counter starts at 1; `expectedVersion` is an integer >= 1.
- Error codes finalized (D03) in `shared/src/errors.ts` with a retry-policy table; additions to the LLD list: NOT_FOUND 404, PAYLOAD_TOO_LARGE 413, IDEMPOTENCY_RESULT_EXPIRED 410, INTERNAL_ERROR 500, NOT_IMPLEMENTED 501 (I1 stubs only), SERVICE_UNAVAILABLE 503. Malformed envelope/headers = INVALID_REQUEST; invalid `command` = INVALID_COMMAND.
- Idempotency-Key: printable ASCII, 8-128 chars. Request body limit 1 MiB. Validation error details carry paths and messages only, never submitted values.
- Authentication runs before validation on every `/v1/diagrams/*` route (scoped hook); the I1 default authenticator rejects everything with 401 until I3.

## I2 engine choices (2026-10-05, default)
- Engine: `server/src/modules/diagrams/domain` (`applyCommand(doc, command, newId)`): pure, returns `{ok,value}` or `{ok:false,error:{reason,message,details}}`; reasons are the shared DOMAIN_ERROR_REASONS and map to DOMAIN_VALIDATION_FAILED (422) with `details.reason`. A post-condition check throws if the engine ever produces an invalid document (a bug, never a user error).
- Prototype behaviours consciously changed: addNode of an existing id (no-op) -> ids are server UUIDs, same-name nodes are allowed; insertBetween used to drop relationship and delete both directions -> now removes one directed edge and both replacement edges copy relationship and metadata; disconnect removed both directions -> removes exactly one directed edge (edgeId, or source+target if unambiguous); renameNode re-inferred icon/subType -> rename touches only the name.
- Placement (P2 refinement): new nodes start at the insert midpoint (INSERT_BETWEEN) or the dagre position (ADD_NODE), then move to the nearest free spot (40 px clearance, alternating down/up in 130 px steps) so they never overlap and no existing node moves. Found by checking the first version in the browser: preserving positions alone stacked Redis on PostgreSQL.
- Dev preview: `/dev/engine/*` API routes exist only when NODE_ENV=development (404 in test/production) and `engine-demo.html` + `src/dev/engine-demo.ts` (not in the production build). Remove or keep behind the flag once the real editor (I4) is the way to see changes.

## I3 persistence and API choices (2026-10-05, default; veto welcome)
- Local database without Docker: `embedded-postgres` (real Postgres 18.4 binaries, devDependency) powers `npm run dev:db -w @tinker/server` (persistent, loopback, throwaway credentials) and an isolated per-run cluster for tests. Docker Compose file kept as an alternative. Target hosting remains Supabase Postgres (S4) and was not exercised.
- Tables as in LLD section 2 plus `workspaces.personal_for_user_id` (unique bootstrap key, D09) and generic `mutation_requests` (D01) linked from `command_executions`. `command_executions.idempotency_key/payload_hash` of the LLD are replaced by the link to `mutation_requests`. All tables have RLS enabled with no policies; anon/authenticated roles are revoked when present.
- Version semantics: new diagram = version 1; every durable change (command, presentation save, rename, delete) = +1. Revisions (MANUAL_COMMAND) only for structural commands; presentation saves, renames and deletes create none (supersedes nothing; revisit with I8 restore).
- Authorization order: authenticate -> rate limit -> request shape (params, headers, body schema) -> authorize (404 for non-members/deleted, 403 for insufficient role) -> idempotency reservation -> version/domain checks -> atomic commit that re-authorizes. Replays always pass authorization first, so revoked or deleted access never replays; a retried DELETE after the diagram is gone answers 404 (D09).
- Stored outcomes: success and deterministic failures (409 version conflict, 422 domain refusal) are stored and replayed (D03). Auth failures and infrastructure errors are not cached: the reservation is released so the key can be retried. Replay window 7 days, then 410 IDEMPOTENCY_RESULT_EXPIRED (cleanup job in I8). Lease 60 s, MAX_ATTEMPTS 3 (used by the I5 provider path).
- Request hash = sha256 of canonical JSON {api v1, method, resource path, validated body}; expectedVersion is part of the body (DELETE: the validated query).
- DELETE contract: `DELETE /v1/diagrams/{id}?expectedVersion=n` (soft delete, version +1). Empty bodies with `Content-Type: application/json` are accepted.
- Auth: Supabase JWKS verification (`jose`, asymmetric algorithms only, issuer `<SUPABASE_URL>/auth/v1`, audience `authenticated`); user mapped by `sub` to `users.external_auth_id`; no token or membership caching in the MVP (revocation takes effect on the next request; cost to be measured in I9). Local development login (`AUTH_MODE=dev`, `POST /dev/auth/login`) signs tokens with a throwaway in-memory key and exists only if explicitly enabled AND NODE_ENV=development; production config rejects it and requires SUPABASE_URL, DATABASE_URL and CORS_ORIGINS. The dev key changes whenever the API restarts, so sessions end on restart.
- Rate limit: fixed window, in-memory, per user, 120 requests/minute (`RATE_LIMIT_PER_MINUTE`), 429 with Retry-After (single-instance only, D10).
- CORS exposes `x-request-id`, `idempotent-replayed` and `retry-after` so the I4 client can read them.
- Workspace/member management routes (create workspace, invite, roles) are NOT built; tests grant roles directly in SQL. Diagram listing is capped at 200 without pagination.

## I3 Supabase wiring (2026-10-05)
- Project: `rnwbgjrzbliqvqradjcm` (region ap-southeast-1, Postgres 17). URL is not a secret and is in `server/.env.supabase.local` (gitignored via `*.local`). The browser-side publishable key is public by design; the boundary check now allows `VITE_*PUBLISHABLE*` names but still rejects other `VITE_*KEY/SECRET/TOKEN/PASSWORD`.
- Schema applied to the Supabase project through the Supabase connector (`apply_migration` named `initial_schema`), then recorded in node-pg-migrate's `pgmigrations` table so `npm run db:migrate` against Supabase is a no-op. Future migrations: apply with `npm run db:migrate` once `DATABASE_URL` is set (preferred) so both tools agree.
- Database TLS is explicit: `DATABASE_SSL=off|verify|no-verify` (+ `DATABASE_SSL_CA_FILE`). `sslmode` in the URL is stripped so the policy cannot be overridden by a pasted Supabase URL. `no-verify` is rejected in production. Use the Supabase session pooler (port 5432) for the API; transaction-mode pooling (6543) is untested.
- The API must connect as a role that owns the tables or bypasses RLS (Supabase `postgres` does both); `check:supabase` verifies this because otherwise RLS-with-no-policies would make every read silently empty.

## Signing-key handling (2026-10-05)
- Replaced jose's remote JWKS cache with `server/src/infrastructure/auth/key-store.ts`: refresh keys every 5 min (`cacheMaxAge`; also the longest a revoked key keeps verifying while Supabase is reachable), at most one fetch attempt per 30 s (cooldown, also during outages and for unknown-key floods), single-flight fetches, last good keys usable for up to 1 h if Supabase is unreachable, then 503. Provider failures (HTTP error, non-JSON, timeout, garbage) are 503 `SERVICE_UNAVAILABLE`; only token problems are 401. A token signed with a brand-new key can be refused for up to the 30 s retry gap right after rotation (Supabase publishes the new key before using it, so this should not occur in practice).

## I4 editor choices (2026-10-05, default; veto welcome)
- Structure: `src/api/client.ts` (typed client, transport retries with the SAME idempotency key and body, one credential refresh on 401), `src/document/session.ts` (the only writer of the document: one serialized queue per diagram, conflict/draft handling), `src/auth/auth.ts` (Supabase via supabase-js, plus the dev login in `npm run dev` only), `src/workspace/workspaceStore.ts` (bootstrap, open/create/rename/delete), `src/diagram/{store,adapters,flow,inference}.ts` (editor view over the session). The Zustand diagram store is a VIEW over the session, never the source of truth.
- Structural edits are CONFIRM-THEN-APPLY: the canvas changes when the server acknowledges (a Saving badge shows meanwhile). This replaces D04's optimistic ghost nodes for now (LC15). Drag position saves ARE optimistic through an overlay and are saved after 350 ms of quiet, coalesced, in order with structural edits.
- expectedVersion is captured when a write is first sent and reused unchanged on retries, so a retried write is byte-identical and replays rather than re-applies. A transient failure holds the queue ("Not saved - Retry"); `online` events and the Retry button resume it.
- Conflict (409): the queue stops, unsaved work is kept as a draft in localStorage (`tinker_draft_<diagramId>`), and the user chooses "Load latest (discard mine)" or "Re-apply my changes on latest" (new keys, new version; refusals are counted). Window focus quietly picks up other-tab changes when nothing is pending.
- Leaving: switching diagrams waits for the queue (or asks before discarding); closing the tab warns while work is unsaved.
- Command mapping: add -> ADD_NODE (icon in `metadata.icon`, technology = the old subType); connect -> CONNECT; edge delete -> DISCONNECT by edge id; node delete -> REMOVE_NODE only (React Flow incident-edge deletions are not sent separately); edit dialog -> RENAME_NODE + UPDATE_NODE (only what changed); advisor suggestions -> INSERT_BETWEEN when an edge exists, otherwise add + two connects (ids are server-assigned, so steps wait for each other); group -> UPDATE_NODE `metadata.group` (shown as a tag); reset -> RESET after confirmation; auto layout -> one position save of all nodes.
- Removed: undo (LC14), the in-browser Gemini orchestrator/voice clients and the Settings modal (moved to `legacy/prototype-ai/` as I5/I7 input), the Gemini model badge. The command bar and empty-state prompts are visibly disabled until I5/I7.
- Security: the browser holds no provider secret. `check:boundaries` now has no exemptions and also fails on any browser reference to Gemini endpoints or SDKs and on aliasing the whole `import.meta.env` (which would embed every VITE_* variable from a developer's `.env`). The `npm run build` output was checked for Gemini key shapes (none).
- Browser configuration: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, optional `VITE_API_URL`; if absent the sign-in screen lets the user enter the Supabase URL and publishable key once (kept in localStorage; both are public values).

## I5 typed-command choices (2026-10-05, default; veto welcome)
- Flow (POST /v1/diagrams/{id}/ai/command): authenticate -> rate limit -> request shape -> authorize -> conversation ownership check -> idempotency reservation -> cheap version pre-check -> AI rate limit + concurrency slot -> interpret OUTSIDE any transaction under one hard deadline -> dry-run the plan on the loaded version -> ONE transaction (fence the lease, re-authorize, version must still equal expectedVersion, apply, revision `AI_COMMAND`, execution record, conversation turn, stored response). The interpretation is bound to the version the user saw: if the diagram moved meanwhile nothing is applied (409).
- Two interpreters behind one gateway: a deterministic parser (no model; plain commands such as insert-between, add, connect, disconnect, remove, rename) and the model for everything else. References must resolve to exactly one component (exact name, else an unambiguous partial name, else a UUID); unknown or ambiguous references become clarification questions. A request with no connection between the two nodes of an insert is wired in (ADD_NODE + two CONNECT), a reversed connection asks which direction.
- The model never sees or invents UUIDs: it works with aliases (n1.., e1.., new1..) resolved server-side. Its output must pass a strict schema (no unknown fields or step types, at most 8 steps) or it counts as a provider failure. RESET is not available to the model, and a typed reset is answered with a pointer to the confirmed Reset button.
- A plan is ALL OR NOTHING and commits as ONE version regardless of step count; any engine refusal refuses the whole plan (422 with reason and step index). Executions are recorded as `PARSER_PLAN` / `AI_PLAN`.
- Provider failures (D03/D07): one upstream retry inside the remaining deadline, total deadline 15 s (`AI_DEADLINE_MS`), late results ignored (lease fencing plus a deadline race that does not depend on the provider honouring cancellation). Transient failures mark the key RETRYABLE_FAILED (no response stored, up to 3 same-key attempts; afterwards 503 AI_UNAVAILABLE without calling the provider); auth/disabled/rejected failures release the key. Mapping: timeout 504, unavailable/bad output/rejected 502, rate limited/auth/disabled 503.
- Limits: 10 AI requests/minute/user (`AI_RATE_LIMIT_PER_MINUTE`) and 2 simultaneous (`AI_MAX_CONCURRENT`), in memory, single instance (D10). Stored replays do not consume them.
- Conversations: one conversation per (diagram, user); the first typed command creates it, the client sends its id afterwards; ownership and diagram are checked before any work. USER and ASSISTANT turns are stored once per logical request inside the same transaction as the outcome; provider failures store nothing. Context for the model: last 6 turns (500 chars each, 4 KB total), diagram text up to 24 KB (larger diagrams get a clarification asking for a precise command). GET /v1/diagrams/{id}/conversation returns the caller's latest conversation (oldest first, 50 messages).
- Gemini integration (read from the docs on 2026-10-05): plain `fetch` to the Interactions API (`POST /v1beta/interactions`), key only in the `x-goog-api-key` header, `store:false`, `response_format` JSON schema, model `GEMINI_MODEL` (default `gemini-3.8-flash`, confirmed as a current stable model), redirects refused, response text located tolerantly because documentation summaries disagree on field names. No SDK so deadline and cancellation stay under our control. Never logged: the key, user text, provider-echoed text.
- `GET /v1/me` reports `features.aiCommands` (typed commands offered: always true, the parser needs no model) and `features.aiModel` (a model is configured). Without a key plain typed commands work and free-form ones answer 503 with a friendly message; manual editing is unaffected (acceptance A18).
- Browser: typed commands are another item in the serialized document queue (same idempotency key on lost-response retries, bound to the on-screen version). Provider failures and rate limits are NOT retried automatically by the client (each attempt can take the full deadline); the failure appears in the chat and the text stays in the bar. The Conversation tab shows the persisted conversation; clarification options fill the bar and are never sent automatically.

## I5 live Gemini findings (2026-10-06)
- `gemini-3.8-flash` was overloaded/slow with the user's key (503s, hangs), so the default is `gemini-3.5-flash-lite` with thinking level `low`: typical answer 1.5-2.5 s, occasional 7-13 s.
- The first provider attempt is capped at half the 15 s deadline so a hung call is retried once inside the same deadline. Exact repeated non-ADD steps are dropped; empty/over-long optional text is dropped; nodes created without `as` are addressable as new1, new2.
- Remaining model noise (about 1 in 6 free-form requests): an incomplete plan (missing connect) or a step the engine refuses. Failures never half-apply (plans are atomic) and show a clarification or error. Revisit with `GEMINI_THINKING_LEVEL=medium` or a bigger model if it bothers users (LC23).

## I6 read-only advice (2026-10-06)
- Advice needs `view` access (a viewer can ask), has no idempotency key (nothing is mutated, a network retry is safe) and stores only the question/answer turn in the caller's own conversation. It shares the AI rate limit and concurrency cap with commands.
- The graph analyzer (no model) computes the facts; the model only explains them. Direction: an edge A -> B means A sends to B; downstream = what X sends to, upstream = what sends to X. "Affected" for highlighting = the mentioned components plus both directions (the blast radius).
- Mentions are found by whole-word component name, case-insensitive, longest name first. When a question names nothing, the model still sees every component's reach (diagrams up to 40 components) and may pick highlights, which must be real aliases.
- Any provider failure, timeout or invalid model output falls back to a computed answer (source `ANALYZER`) instead of an error, so advice works with no key.
- The UI routes anything ending in "?" to advice, except polite requests ("can you add Redis?"), and has an Ask/Edit switch. Highlights are view state and are never saved.

## I7 voice contract (D08 resolved, 2026-10-06)
- Transport: `GET /v1/voice` upgraded to WebSocket; allowed Origin required; the access token travels in the first `hello` message, never in the URL (URLs get logged); `hello` must arrive within 5 s. Text frames are JSON (validated both ways), binary frames are audio (client to server only).
- Audio: raw 16-bit little-endian PCM, 16 kHz, mono, frames of about 100 ms (max 16 KB). The server relays to Gemini Live (`gemini-3.8-live`, verified with the real key; configurable with `GEMINI_LIVE_MODEL`). Model audio replies are discarded: the model is only the "ears" (speech to a written request).
- The model has exactly two tools: `edit_diagram(request)` and `ask_about_diagram(question)`. The server then treats the text exactly like a typed command or question (parser fast path, then the structured-output model, same validation, idempotency and atomic commit). One interpretation path, not two. Partial transcripts are display only.
- Binding: the browser reports the diagram version it has on screen (`context`); a proposal commits only against that version (stale => conflict, nothing applied). Each proposal has a stable operation id and an idempotency key derived from the session and the tool call id; a repeated tool call id is ignored.
- Limits (D10): one session per user (newer replaces older), 20 sessions server-wide, 10 min per session, 45 s of silence, sustained audio 64 KB/s, provider backpressure drop-then-close, 3 pending proposals; proposals share the AI rate limit (10/min) and concurrency cap.
- Failure behaviour: permission is re-read on every proposal and every 15 s (removed => close 4404; viewer => edits refused, questions allowed); an expired token closes with 4401 unless refreshed with `auth`; if the model connection drops the session stays up, says so, and `start` can be repeated; nothing about voice can block typing or manual editing. Reconnecting never replays committed commands: a new session has new ids, and the browser re-syncs the diagram and conversation from the server first.
- Spoken replies (added the same day): see the next section. Not built (deliberately): provider session resumption, per-user cost metrics (LC31), multi-instance session registry (LC32).

## I7 spoken replies (2026-10-06)
- The assistant's reply to a SPOKEN request (answer, question back, or edit confirmation) is read aloud; typed requests stay silent.
- Two voices, user's choice, remembered in the browser: Gemini (natural, uses Gemini speech quota) and the browser's built-in voice (free, more robotic), plus Off. Default is Gemini when the server reports `features.speech`, otherwise the browser voice. If Gemini fails (quota, outage, timeout) that reply is read with the browser voice instead.
- Server: `POST /v1/diagrams/{id}/ai/speak {messageId}`; view access; only the caller's own ASSISTANT messages; no free text; text cleaned and cut to about 220 characters at a sentence; models tried in order (`GEMINI_TTS_MODEL`, default `gemini-3.8-flash-tts,gemini-3.8-flash-lite-tts`; the older preview speech models allowed only ~10 requests a day on this key); covered by the AI concurrency cap and the ordinary request limit.
- While a reply plays the browser stops streaming the microphone (plus 0.4 s) so the assistant does not hear itself; starting to speak again stops playback.
- Echo guard for tool calls: same-kind request with at least 70% the same words within 10 s is the same request (a failed one may be repeated).

## I8 history, restore and maintenance (2026-10-06)
- Restore (D11): `POST /v1/diagrams/{id}/restore {expectedVersion, version}` makes the diagram look like that revision as version current+1 (RESTORE revision, execution record, idempotent, version-checked, atomic). It never decrements the version. A missing revision is a 422 `REVISION_NOT_FOUND` (not 404, so a client cannot mistake it for a missing diagram); restoring the content already shown is a 422 `ALREADY_CURRENT`. History is readable with view access; restoring needs edit access.
- Drags and renames create no revision (D05), so version numbers have gaps and the history lists structural changes only. A new diagram now gets a baseline CHECKPOINT revision (version 1, empty) so the very first change can be undone; diagrams created before I8 have no baseline.
- Undo/redo are restores, not a local snapshot stack: durable, visible in the history, working across refresh and devices. Undo goes to the nearest earlier version whose content differs; Redo restores the version we came from; any other change to the diagram's content forgets Redo (a drag does not).
- Retention (D11): a revision is pruned only when it is outside the latest 100 AND older than 30 days (intersection bound). The product copy says exactly this. No pinned checkpoints yet.
- Replay policy: full response replay for 7 days, then the body is dropped and the request row stays as a tombstone (the key keeps answering "expired" and never re-executes); diagnostics (`command_executions`) are kept 90 days; tombstones are removed after 90 days. In-flight requests are never touched.
- Deleted diagrams: soft-deleted for 30 days, then purged by the worker with everything attached, one diagram per transaction. There is no recovery API yet (LC35).
- Jobs (D12): Postgres table, `FOR UPDATE SKIP LOCKED` short claim, lease with heartbeat, a lease token that completion/failure/heartbeat must present (fencing), 3 attempts with 10 s and 60 s delays then DEAD_LETTER, sanitized one-line errors with a kind, deterministic operation keys for enqueue, hourly scheduling by the worker itself. Only the three maintenance types exist; export and deep-analysis jobs wait for acceptance criteria. The worker is a separate process (`npm run worker`); it is not started by the API.

## I9 release readiness (2026-10-06)
- Plain commands the parser understands no longer count against the per-user AI limit or concurrency cap: those limits apply only when the model is actually needed.
- The per-request user lookup is one read with no transaction when the user, personal workspace and membership exist and the token adds nothing new; the full upsert transaction runs only on first sight or a changed email or name.
- One structured `request` log line per API call (route pattern, status, milliseconds, error code) replaces Fastify's two default lines (which print full URLs with ids). Logs never contain bodies, tokens, prompts, ids or user text.
- Backups: the managed provider's backups are not available on the Free plan, so a provider-independent logical backup (`backup:drill`) is part of the product's recovery story; it runs on a consistent read-only snapshot and verifies by checksum. Hourly runs would bound the loss window to one hour.
- Sign-in: Supabase PKCE with session detection in the address; Google, password reset and confirmation links all return to the app's own origin, which must be allowed in Supabase. The password-reset answer never reveals whether an address has an account.
- One line-ending policy (`.gitattributes`, LF) because Windows checkouts broke a script with a `#!` first line.
